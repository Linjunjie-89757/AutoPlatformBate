# Figma 页面对齐与验收规范

> 适用范围：自动化测试平台 2.0 的 Vue 页面、组件、弹窗、抽屉和浮层
>
> 配套台账：`设计/遗留问题.md`；如项目另行维护《Figma 待补设计与视觉差异台账》，以最新台账为准
>
> 更新日期：2026-09-01

## 1. 目的

本规范用于统一页面从 Figma 设计到 Vue 实现的核对、修改和验收方式，避免只检查默认态、只验证页面能打开，或遗漏旧 DOM、旧文案、旧交互和异常状态。

台账负责记录“哪些页面需要处理以及当前状态”；本规范负责说明“每个页面具体如何核对以及什么条件下可以关闭”。

## 2. 信息优先级

不同来源发生冲突时，按以下顺序处理：

1. 最新且已确认的产品业务规则，包括明确的产品例外。
2. 最新且可定位的 Figma Design 节点。
3. 最新 Figma Make 代码表达的布局、组件和交互意图。
4. 当前 Vue 页面、公共组件和后端接口的实际约束。
5. 历史问题记录、旧设计稿和过期截图。

Figma 示例数据与真实业务数据不一致，不属于视觉缺陷。不得为了让截图数字一致而修改真实数据。

React 和 Vue 的 DOM 不要求逐字节相同；要求用户可见的布局、视觉结果、状态和交互行为一致。Element Plus 可以作为实现基础，但不能因为使用 Element Plus 就默认认为已经符合 Figma。

## 3. 台账状态

台账中的每个条目同时记录“设计状态”和“实现状态”，不要混为一个状态。

### 3.1 设计状态

| 状态 | 含义 |
| --- | --- |
| 已有 Design | 有可定位的 Figma Design 节点，可进行尺寸和视觉验收 |
| 仅有 Make | 有 Make 代码或预览，但没有正式 Design 节点 |
| 需 Figma 补稿 | 入口、状态或业务流程没有足够的设计基准 |
| 需产品决策 | 设计和业务规则冲突，不能由前端自行取舍 |
| 文档冲突 | 旧记录与较新的 Design、Make 或产品结论不一致 |

### 3.2 实现状态

| 状态 | 含义 |
| --- | --- |
| 未实现 | 页面或能力尚未实现 |
| 部分实现 | 主流程存在，但状态、权限或异常流程不完整 |
| 已实现待验收 | 代码已修改，但尚未完成运行态截图和交互验收 |
| 已关闭 | 设计、实现、运行态和测试证据均已记录 |

## 4. 开始前的输入

每个页面开始前必须收集并记录：

- Figma Design 链接和准确的 `node-id`。
- Figma Make 代码目录、分支或提交版本。
- 本地 Vue 路由和目标组件文件。
- 可用的登录账号、工作区和真实测试数据。
- 本次允许修改的页面范围。
- 已确认的业务规则和例外，例如“已正式采纳不可撤销”。
- 页面需要覆盖的后端接口和权限范围。

如果没有准确 Design 节点，只能标记为“仅有 Make”或“需 Figma 补稿”，不能声称已经完成 1:1 视觉对齐。

## 5. 三层核对方法

### 5.1 Figma Design

记录节点结构和可量化规格：

- 页面、抽屉、弹窗和浮层的宽度、高度及定位。
- Header、Body、Footer 的层级和分隔关系。
- 内外边距、网格、间距、对齐方式和滚动区域。
- 字体、字号、字重、行高、颜色、边框、圆角和阴影。
- 图标来源、尺寸、颜色和按钮中的对齐方式。
- 默认、hover、focus、selected、disabled、loading、empty、error、success 状态。

### 5.2 Figma Make

阅读对应组件和状态分支，记录：

- 组件层级和条件渲染关系。
- 状态枚举、状态转换和允许的操作。
- 按钮文案、提示语、确认语义和错误恢复方式。
- 批量操作的全部成功、部分成功和全部失败处理。
- 长文本、数量为 0、缺少字段和未知值的显示逻辑。

Make 代码是行为和结构参考，不应直接复制 React/Tailwind 代码到 Vue 项目。

### 5.3 本地 Vue 运行态

在与设计相同的视口和业务状态下检查：

- 真实 DOM 层级和组件边界。
- `getBoundingClientRect()` 的尺寸和位置。
- computed style，包括字体、行高、颜色、间距、边框、圆角、阴影和透明度。
- 真实接口返回的数据、加载状态、错误状态和权限状态。
- 用户操作后的状态变化、按钮禁用、Toast、弹窗和路由行为。

设计工具提供目标规格，运行态验证最终结果；两者缺一不可。

## 6. 状态矩阵

修改前先为页面建立状态矩阵。至少包含以下状态；不适用时注明原因，不可默认为“已覆盖”。

| 状态 | 要检查的内容 |
| --- | --- |
| 默认 | 页面结构、数据展示、主操作和初始选中状态 |
| hover | 背景、边框、文字、图标和操作按钮显隐 |
| focus | 键盘焦点、输入框边框、按钮焦点和可访问名称 |
| selected | 选中背景、文字、批量工具条和联动数量 |
| 编辑 | 字段、占位文案、保存/取消、校验和是否隐藏只读内容 |
| loading | 骨架或加载文案、按钮 loading、表单禁用和重复提交保护 |
| disabled | 禁用原因、颜色、鼠标行为和后端权限一致性 |
| empty | 无数据、空态说明、主操作和容器尺寸 |
| error | 错误文案、重试、保留输入和失败后的状态恢复 |
| success | 成功状态、Toast、后续操作和数据刷新 |
| 未保存 | 关闭、返回、取消或路由离开时的确认行为 |
| 权限 | 无查看、无操作、后端 403 和按钮禁用 |
| 并发 | 版本冲突、重复提交和刷新后的最终状态 |
| 长数据 | 长标题、长错误、长步骤、数量为 0 和未知值 `—` |

对于涉及状态机的页面，还要记录每个状态允许和禁止的操作。例如 AI 用例：

```text
待采纳 → 采纳中 → 已采纳
                 ↘ 采纳失败 → 重试
待采纳 → 已放弃 → 待采纳
已采纳 → 不允许撤销
```

## 7. 逐项视觉检查清单

逐项勾选，不用“整体看起来差不多”替代：

- [ ] 页面或面板宽度由正确的容器规则控制，未误用固定宽度。
- [ ] Header、Body、Footer 的高度和边界正确。
- [ ] 标题、副标题、标签、状态 Badge 的位置和层级正确。
- [ ] 字体、字号、字重和行高正确，中文没有溢出或截断异常。
- [ ] 内容区内边距、组件间距和对齐线正确。
- [ ] 按钮顺序、位置、宽高、圆角、文字和 loading 状态正确。
- [ ] 图标使用项目图标库或明确的设计资源，没有手写字符替代图标。
- [ ] 旧标签、旧表单、旧 footer、旧分隔线和旧提示节点已清理。
- [ ] 长内容可以滚动，footer 不被内容挤压，窄屏不产生不可用溢出。
- [ ] 空态、错误、成功和权限状态仍使用同一套页面规则。

## 8. 逐项交互检查清单

- [ ] 点击区域与设计一致，例如整行、按钮或图标的触发范围。
- [ ] 操作进行中按钮和相关输入已禁用，不能重复提交。
- [ ] 成功后状态、数据、统计和可用操作正确更新。
- [ ] 失败后保留用户可恢复的数据，并提供符合语义的重试或返回。
- [ ] 取消、关闭、返回和路由离开符合未保存确认规则。
- [ ] 批量操作分别验证全部成功、部分成功和全部失败。
- [ ] 已完成或已采纳状态没有错误的反向操作。
- [ ] 失败项重试不重复要求已经保存且仍有效的配置，除非路径确实失效。
- [ ] 刷新或重新进入页面后，后端持久化状态和页面显示一致。

## 9. 接口与数据验收

页面接入真实业务时，除了视觉检查，还要确认：

- 前端状态不是只保存在内存中。
- 关键状态刷新后仍然存在，失败原因不会无故丢失。
- 正式对象创建与任务状态更新不会造成重复创建。
- 后端具备幂等、唯一约束、版本号或乐观锁中的适当保护。
- 错误码和错误文案能正确回显到当前页面。
- 权限和前端按钮状态与后端校验一致。

如果后端能力尚未完成，应在台账中标记为“部分实现”，不能用前端模拟状态代替正式闭环结论。

## 10. 截图和运行态证据

每个页面至少保留：

- 默认态截图。
- 主要业务状态截图。
- 编辑态截图。
- loading 或 disabled 截图。
- error 或失败恢复截图。
- 批量或异常状态截图（页面涉及时）。

截图必须记录：

- 页面路由和业务状态。
- 视口尺寸和浏览器环境。
- Figma 节点 ID。
- Make 代码路径和版本。
- Vue 页面路径。
- 截图文件路径。
- 验证日期。

截图只证明该状态的运行态结果，不能替代其他状态的验收。

## 11. 验证命令

根据改动范围执行：

```text
npm run typecheck
npm run build
后端对应模块测试
git diff --check
```

需要真实页面验证时，使用 Playwright：

1. 打开页面并登录。
2. 获取最新 snapshot，再使用元素引用操作。
3. 每次导航、弹窗、抽屉或状态变化后重新 snapshot。
4. 保存关键状态截图到 `output/playwright/`。
5. 检查 DOM、bounding box、computed style 和控制台错误。
6. 完成后恢复测试数据，不留下临时采纳、删除或编辑状态。

## 12. 台账关闭标准

只有同时满足以下条件，条目才能标记为“已关闭”：

1. Design 节点、Make 代码和产品规则的冲突已经处理并记录。
2. 状态矩阵中的适用状态全部检查完成。
3. 视觉清单和交互清单全部通过，或明确记录产品例外。
4. 真实接口、失败恢复、权限和刷新行为已经验证。
5. 截图、节点 ID、视口和验证日期已留档。
6. 类型检查、构建、相关测试和 `git diff --check` 通过。
7. Git 提交只包含本次相关文件，没有带入临时文件或用户未提交改动。

缺少正式 Design 节点但已按 Make 或相邻页面延展实现的条目，只能标记为“已实现待视觉验收”，不能写成“Figma 1:1 已关闭”。

## 13. 推荐实施顺序

1. 先处理阻塞核心创建、编辑、执行和保存的 P0 视觉差异。
2. 再处理核心业务链路缺失的 Design 和异常状态。
3. 再处理高频管理流程、批量操作、权限和并发状态。
4. 最后处理低频入口、窄屏适配和轻微像素差异。
5. 定期清理与最新产品结论冲突的历史记录，避免旧问题重复派发。

每次完成一个页面后立即回写台账，不把多个页面的未验收状态混在一次结论中。
