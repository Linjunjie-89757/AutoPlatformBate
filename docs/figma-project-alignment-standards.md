# AutoTest 项目 Figma 对齐准则

## 1. 文档定位

本文档是 AutoTest 项目进行 Figma 页面、弹窗、抽屉、表格和组件对齐时的统一入口。

项目技术栈：Vue 3、Element Plus、Pinia、Vue Router。

本文档只规定项目内的对齐原则和验收门槛，不要求把 Figma Make 的 React、Tailwind、Radix 或 shadcn 代码直接迁入当前项目。

相关文档：

- `docs/figma-design-alignment-method.md`：通用执行流程和操作方法。
- `docs/figma-visual-restoration-guide.md`：项目详细视觉约束、历史漏检问题和验收清单。
- `设计/遗留问题.md`：无法在当前任务内解决的设计、交互和业务差异。

本文件与 `AGENTS.md` 中的六步门禁共同作为当前执行入口。上述历史参考文档若出现“唯一权威”、跨视觉/业务的单一优先级、默认容许偏差或更宽松的完成口径，以本文件的分领域裁决和验收要求为准；用户本次明确指令优先。不得选择较宽松的旧条款绕过门禁。

结构化验收记录使用 `docs/figma-alignment-record.template.json`，保存到 `docs/figma-alignment/`。文字总结只能辅助说明，不能替代证据记录。

## 2. 三条裁决线

### 视觉

```text
Figma Design > Figma Make > 当前代码
```

Design 决定最终的颜色、尺寸、字体、字重、行高、间距、圆角、阴影、图标和布局。

### 交互

```text
Figma 动态说明 / Make 事件和状态 > 当前代码
```

Make 用于确认点击、Hover、Focus、Active、Tab、筛选、展开、提交、加载、错误和重试等行为意图。

### 业务

```text
真实业务规则、接口、权限、数据安全和审计 > Figma / Make 演示逻辑
```

设计稿不能覆盖真实的权限、状态流转、版本、并发、幂等和持久化规则。不能使用假数据或假成功状态掩盖后端能力缺口。

Design、Make 和现有业务不一致时，必须记录差异和最终裁决，不得直接宣称“完全一致”。

### 四方证据与冲突处理

Design、Make 源码、Make 预览、当前 Vue 相互佐证，不能套用一个覆盖所有事项的总优先级：

| 来源 | 必须核对的内容 | 不能替代的证据 |
| --- | --- | --- |
| Design 节点和截图 | 默认静态外观、各变体、图标与文案 | 不能用默认截图推断全部动态行为 |
| Make 源码 | 事件、条件分支、状态、CSS、共享组件和文案 | 不能只凭源码声明认定浏览器效果 |
| Make 预览 | 对应版本代码实际运行的外观和行为 | 不能忽略预览与本地代码的版本差异 |
| 当前 Vue 浏览器 | 实际外观、状态变化、业务结果 | 不能用构建通过或旧截图代替 |

- 用户明确指定某项采用 Make（例如 Basic 用户名 placeholder）时，记录该决定并执行，不必再次等待产品确认。
- 同一项在 Design 与 Make 中冲突时，按视觉、交互、业务三条裁决线处理并保留两边证据；无法裁决的关键冲突才询问用户，其余独立工作继续。
- Design 没有独立动态状态稿而 Make 有实现时，按 Make 源码及预览验证该行为；不能以缺少 Design 状态稿为由停止实现或声称该行为无法验收。
- 当前组件库自带的 Hover、Focus、动效或文案不是设计依据。决定保留时必须登记实际偏差及依据，不能以“沿用项目习惯”自动宣称与 Make 一致。

## 3. 开始前的基线

每次对齐任务开始前必须确认：

```text
Git 分支和当前提交
git status
Figma 文件链接和 node-id
Design frame 尺寸
Make 代码目录或版本
目标页面、弹窗、抽屉或组件
允许修改的文件
明确不修改的文件
```

存在用户未提交修改时：

- 先识别并保留已有工作；
- 只做当前目标所需的增量修改；
- 不使用 `git reset --hard`、`git restore`、`git checkout --` 或整文件覆盖；
- 复杂视觉任务应创建可定位的 checkpoint 或提交，便于选择性回滚。

## 4. 范围盘点、六步流程与四方对照

先锁定用户指定范围，在范围内穷举变体和状态。用户仅要求修复一处文案时，只修复该项并回归受影响内容；用户要求整个 Auth 时，必须逐一核对五种类型。不得擅自把局部任务扩展到整页，也不得用一个变体的结果代替其他变体。以下清单按本次范围选用：

```text
页面外壳、标题、面包屑、Tab
搜索、筛选、排序、分页
目录树、表格、操作列
弹窗、抽屉、详情内容
空态、加载态、成功态、错误态、失败重试态
权限不足、长文本、窄屏和滚动区域
```

按顺序完成六步，每一步保留证据；第 1 步是确定目标规格，代码实施在第 4 步：

1. 读取准确 Design 节点和截图，建立各变体的默认静态规格。
2. 读取 Make 源码，列出目标区域事件、状态、条件渲染和文案。
3. 在 Make 预览逐项操作，记录实际结果并检查其与本地 Make 版本是否一致。
4. 基于前三步差异表增量修改 Vue，保留真实业务约束。
5. 在真实浏览器逐一验证 Vue 变体和状态，保存截图、computed style、bounding box 和交互结果。
6. 完成四方差异登记、证据复查、检查脚本和范围限定的交付结论。

差异表必须在修改前建立，并在实施和验证过程中持续更新，不能在结束时凭记忆补写：

| 验收项 / 变体 / 状态 | Design 节点与值 | Make 源码路径与逻辑 | Make 预览操作与结果 | Vue 当前值与结果 | 最终依据 / 差异编号 / 验证方式 |
| --- | --- | --- | --- | --- | --- |
| Basic 用户名 placeholder | 节点原文 | 源码原文 | 空输入框实际文案 | 实际 placeholder | 用户决定采用 Make；浏览器核对 |
| Digest 密码显隐 | 默认图标与尺寸 | 显隐状态及 Eye/EyeOff 分支 | 点击前后图标、输入类型和值 | 同操作结果 | 验证两个方向及值保持 |

继续中断的任务时，先核对当前差异、记录和证据文件，再续做。聊天中的“已完成”、旧记录中的 `verified` 和前一轮构建成功都不能自动成为本轮新结果。

## 5. 视觉实施规则

每个关键控件至少核对：

```text
宽度、高度、padding、margin、gap、对齐方式
字体、字号、字重、行高、字间距
文字、背景、边框、透明度、圆角、阴影
图标类型、尺寸、描边、颜色和位置
换行、溢出、压缩和状态变化时的布局稳定性
```

关键元素必须记录三组值：

```text
Design 目标值
CSS 声明值
浏览器最终 computed style 和 getBoundingClientRect()
```

注意事项：

- CSS 写入目标值不代表浏览器最终生效；必须检查继承、选择器优先级、`box-sizing`、`flex-shrink`、`min-width`、padding 和 border。
- 表格行高、抽屉宽度、按钮尺寸和固定区域位置必须读取实际 bounding box。
- 页面专属样式必须限定作用域，不用全局规则解决局部问题。
- 不以 `!important`、超长选择器或无关全局重构作为默认修复手段。
- 优先复用项目现有 Element Plus、AppDrawer、表格组件和设计 token。
- 逐项核对 label、placeholder、帮助文案、标点和变量占位符；区分输入值与 placeholder，不得把 Design 示例值误当成占位文案。
- 图标需核对存在性、正确资源、描边、可见路径、SVG 尺寸及点击区域；密码显隐必须核对 Eye/EyeOff 两个方向和值保持。DOM 外框尺寸正确不代表可见图形正确。
- 每个变体完成后立即测量；共享样式变动后重新检查全部受影响变体，防止修好 Basic 却压缩 Digest 图标。
- 不得自行将数值四舍五入或把“约 1px”作为通用豁免。存在渲染偏差时记录实测值、环境和影响，按已确定的验收容差或明确决定处理。

## 6. 交互和状态实施规则

按钮、输入框、Tab、标签和操作列至少检查：

```text
默认 → Hover → Focus → Blur → Active / Selected
    → Loading → Disabled → Success → Error → Retry
```

弹窗和抽屉还要确认：

- 打开和关闭入口；
- 遮罩、Esc 和关闭按钮行为；
- 提交期间是否允许关闭和重复点击；
- 未保存内容是否需要确认；
- 内容超长时实际滚动区域；
- 提交失败后是否保留用户输入；
- 成功后是否刷新列表或详情；
- 刷新、返回和分享链接是否保持正确位置；
- 并发修改是否提示版本冲突。

Make 中的空回调、本地数组和演示统计只能作为视觉或交互参考，不能直接视为真实功能。

如果代码或 Make 存在某个状态而 Design 没有单独设计，必须登记为“Design 未提供独立状态”，同时用 Make 源码和预览核对；只有实测吻合后才能报告“该行为已按 Make 验证”，不能冒称存在独立 Design 状态稿。

### 状态存在性与验证状态必须分开

- Hover、Focus、Blur、Active、Disabled、Loading、Success、Failure 必须逐项登记，但不要求为每个控件凭空实现所有状态。八类是检查目录，不是一条控件必经的状态机。
- 未找到 JS 事件处理器不能证明状态不存在：还需检查 CSS 伪类、Tailwind 类、继承和全局样式、共享组件、浏览器原生行为、transition 的属性/时长/easing，并用 Make 预览操作确认。
- `verified` 表示已有源证据，并实际验证了 Make 与 Vue 对应行为；`unverified` 表示尚未验证；`blocked` 表示证据或环境受阻；`failed` 表示验证失败。
- `not-expressed` 仅表示来源没有表达专属状态，必须记录检查范围、Make 源码、预览观察、Vue 的实现决策和实际结果。触发 Focus 后没有专属视觉变化与“不能聚焦”完全不同。
- Design 和 Make 均未表达且业务也不需要的专属状态，不用强行补设计，不算未解决差异。需要新增产品行为、现有实现与来源不一致且无裁决，或用户要求独立像素稿时，才登记补设计/待确认事项。
- 来源读取失败、预览打不开、状态无法触发均不能标为 `not-expressed`；应标为未验证或阻塞，继续其他可完成的核对。
- Vue 保留而 Make 没有的 Hover/Focus 视觉反馈属于实际差异，必须记录。源中没有专属状态不代表 Vue 可以任意新增动效而仍算完全一致。

## 7. 业务与后端边界

```text
Figma 决定显示方式
Make 参考交互方式
真实系统决定是否成功以及何时成功
```

因此：

- 真实接口失败时不能显示假成功；
- 没有持久化接口时不能用前端数组伪造保存；
- 权限、审计、并发、版本和幂等校验不能被视觉实现绕过；
- 设计稿存在但后端尚未支持的入口，应保留真实失败反馈并记录遗留问题；
- 当前系统已有但新版设计没有表达的功能，也不能擅自删除，需记录并等待产品确认。

## 8. 验证要求

### 代码验证

按改动范围执行：

```text
npm run typecheck
npm run build
相关单元测试或接口测试
git diff --check
浏览器控制台和网络请求检查
```

### 页面验证

- 使用与 Design 尽可能一致的 viewport、DPR、浏览器缩放和字体加载状态；
- 使用相同的文案、标点和测试数据比较自适应尺寸；
- 保留 Design 和实际页面的同状态截图；
- 对关键节点保留 computed style 和 bounding box；
- 检查空数据、单条数据、大量数据、长标题、长描述、失败、加载、权限不足、重复点击、窄屏和超长抽屉内容。

不能只根据一张截图或肉眼观感判断整个页面已经完成。

### 证据有效性与门禁边界

- 每条证据须能定位到变体、状态、来源版本/采集时间和实际文件；截图路径必须真实存在。文字“已核对全部五种”不能代替各变体证据。
- 记录实际启动地址、viewport、DPR、缩放、字体加载、测试数据及操作步骤。截图、测量和交互结果必须对应同一实现版本；修改后受影响的旧证据必须更新。
- 允许复用确认未受影响的历史证据，但要说明范围和依据。不能修改一条文案就将整个历史任务从部分对齐升级成完全对齐。
- 执行 `npm run figma:alignment-check -- --record <record.json>`。通过只表明程序能检查的记录约束成立；脚本不能判定截图像素一致，也不能证明文字证据真实。
- 脚本必须拦截非交付状态、未解决差异、未验收/未知事件、空白证据、重复编号和不存在的截图或源码文件。修改门禁后运行 `node --test tools/quality/check-figma-alignment.test.mjs`，同时验证应通过和应失败的用例。
- 类型检查和构建通过只验证代码，不证明视觉或交互对齐。门禁失败时报告具体缺项，不得删掉差异、清空未验收项或改成 `verified` 来凑通过。

## 9. 对齐结论等级

### 完全对齐

仅针对明确声明的范围：六步流程均完成；各变体的 Design 静态规格和 Make 已表达行为均有有效实测证据；未解决差异与未验收项均为零；门禁通过。Design/Make 的来源冲突可以按裁决规则解决，但必须保留冲突记录，不能称四方“完全一致”。没有专属状态的 `not-expressed` 记录本身既不阻止完成，也不能自动证明完成。

### 已验收，存在明确保留差异

必需验证完成，但存在用户明确接受或真实业务约束要求保留的差异。必须报告数量、具体表现、影响及接受依据，不得称“零差异”或“完全一致”。代理自行写“保留项目反馈”不等于用户已接受。

### 视觉已对齐

主要视觉已完成，但后端、真实接口或部分业务状态尚未完成。

### 部分对齐

本次约定范围内仍有未解决差异或未验收内容。用户未要求的其他页面区域不计入本次完成率，不能因为它们未验收而把已完成的局部任务一律判作部分对齐。

### 待确认

Design、Make、现有业务或产品规则存在冲突，需要确认后继续。

只有“完全对齐”可以使用“已完成 Figma 对齐”。其他结论必须明确未完成范围和风险。

机器记录状态使用 `draft`、`partial-alignment`、`blocked`、`verified-alignment`、`accepted-with-deviations`。仅修改状态字段不能改变验收事实；门禁只接受后两种交付状态，且 `verified-alignment` 不允许含保留差异。

最终回复必须区分“已验证、未验证、遗留问题”，给出本次范围内已修复、保留差异、未解决、未验收的数量及证据链接。没有完整覆盖时只能报告“已知差异 N 项，另有 M 项未验收”，不能说“只剩 N 项”或“全部零差异”。

## 10. 遗留问题登记

无法在当前任务内解决的问题统一写入 `设计/遗留问题.md`，每条至少包含：

```text
页面 / Figma 节点
当前代码行为
Design 表达
Make 表达
差异类型：视觉 / 交互 / 后端 / 业务
影响范围和风险
当前临时处理
后续动作：补设计 / 补前端 / 补后端 / 产品确认
```

必须双向登记：

1. Design / Make 有，但系统缺少的能力；
2. 系统已有，但 Design / Make 没有表达的功能、字段、状态或入口。

每条差异分配稳定编号，记录 `status`、`evidence`、`decisionBasis`、`impact` 以及来源、当前表现、处理方式和后续动作：

| status | 含义 | 计数规则 |
| --- | --- | --- |
| `resolved` | 已修复并复验，或按明确裁决选定目标且 Vue 已实测匹配 | 计入已处理，保留历史及冲突来源 |
| `accepted-deviation` | 实际仍有差异，但已有用户决定或强制业务依据保留 | 单独计入保留差异，不得计作消失 |
| `unresolved` | 未修复、未复验、等待取舍或缺少证据 | 计入未解决并阻止完成 |

同一个差异只按其最新状态计数。访问预览曾失败但已恢复属于过程记录，不计作仍存在的 UI 差异；`not-expressed` 属于源状态说明，不直接计作差异。其他实际差异不得因“已有说明”被遗漏。字段写有 resolution 或 followUp 不代表已解决，必须检查内容和证据。

`accepted-deviation` 还须包含 `acceptance` 对象：`type` 为 `user-decision` 或 `business-constraint`，`reference` 定位用户决定或强制业务依据。该字段是可追溯入口，不代表脚本能自动判定接受内容真实有效。
