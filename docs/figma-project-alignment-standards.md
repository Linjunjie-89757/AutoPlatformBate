# AutoTest 项目 Figma 对齐准则

## 1. 文档定位

本文档是 AutoTest 项目进行 Figma 页面、弹窗、抽屉、表格和组件对齐时的统一入口。

项目技术栈：Vue 3、Element Plus、Pinia、Vue Router。

本文档只规定项目内的对齐原则和验收门槛，不要求把 Figma Make 的 React、Tailwind、Radix 或 shadcn 代码直接迁入当前项目。

相关文档：

- `docs/figma-design-alignment-method.md`：通用执行流程和操作方法。
- `docs/figma-visual-restoration-guide.md`：项目详细视觉约束、历史漏检问题和验收清单。
- `设计/遗留问题.md`：无法在当前任务内解决的设计、交互和业务差异。

## 2. 三条裁决线

### 视觉

```text
Figma Design > Figma Make > 当前代码
```

Design 决定最终的颜色、尺寸、字体、字重、行高、间距、圆角、阴影、图标和布局。

### 交互

```text
Figma 动态说明 / Make 事件和状态 > 当前代码
```

Make 用于确认点击、Hover、Focus、Active、Tab、筛选、展开、提交、加载、错误和重试等行为意图。

### 业务

```text
真实业务规则、接口、权限、数据安全和审计 > Figma / Make 演示逻辑
```

设计稿不能覆盖真实的权限、状态流转、版本、并发、幂等和持久化规则。不能使用假数据或假成功状态掩盖后端能力缺口。

Design、Make 和现有业务不一致时，必须记录差异和最终裁决，不得直接宣称“完全一致”。

## 3. 开始前的基线

每次对齐任务开始前必须确认：

```text
Git 分支和当前提交
git status
Figma 文件链接和 node-id
Design frame 尺寸
Make 代码目录或版本
目标页面、弹窗、抽屉或组件
允许修改的文件
明确不修改的文件
```

存在用户未提交修改时：

- 先识别并保留已有工作；
- 只做当前目标所需的增量修改；
- 不使用 `git reset --hard`、`git restore`、`git checkout --` 或整文件覆盖；
- 复杂视觉任务应创建可定位的 checkpoint 或提交，便于选择性回滚。

## 4. 页面盘点与三方对照

不要只修复用户指出的一个按钮。开始实现前，先列出目标区域：

```text
页面外壳、标题、面包屑、Tab
搜索、筛选、排序、分页
目录树、表格、操作列
弹窗、抽屉、详情内容
空态、加载态、成功态、错误态、失败重试态
权限不足、长文本、窄屏和滚动区域
```

建立以下对照表：

| 区域 | Design | Make | 当前代码 | 最终处理 |
| --- | --- | --- | --- | --- |
| 主按钮 | 尺寸、颜色、位置 | 点击和状态 | 模板、CSS、事件 | 保留业务，调整视觉和交互 |
| 表格 | 列宽、行高、标签 | 筛选、分页、行操作 | 接口和组件 | 对齐视觉，使用真实数据 |
| 抽屉 | 宽度、标题、底栏 | 打开、关闭、提交 | AppDrawer 和页面代码 | 局部调整，不重写业务 |
| 空态 | 文案、图形、入口 | 进入和退出条件 | 条件渲染 | 按真实状态实现 |

## 5. 视觉实施规则

每个关键控件至少核对：

```text
宽度、高度、padding、margin、gap、对齐方式
字体、字号、字重、行高、字间距
文字、背景、边框、透明度、圆角、阴影
图标类型、尺寸、描边、颜色和位置
换行、溢出、压缩和状态变化时的布局稳定性
```

关键元素必须记录三组值：

```text
Design 目标值
CSS 声明值
浏览器最终 computed style 和 getBoundingClientRect()
```

注意事项：

- CSS 写入目标值不代表浏览器最终生效；必须检查继承、选择器优先级、`box-sizing`、`flex-shrink`、`min-width`、padding 和 border。
- 表格行高、抽屉宽度、按钮尺寸和固定区域位置必须读取实际 bounding box。
- 页面专属样式必须限定作用域，不用全局规则解决局部问题。
- 不以 `!important`、超长选择器或无关全局重构作为默认修复手段。
- 优先复用项目现有 Element Plus、AppDrawer、表格组件和设计 token。

## 6. 交互和状态实施规则

按钮、输入框、Tab、标签和操作列至少检查：

```text
默认 → Hover → Focus → Active / Selected
    → Loading → Disabled → Success → Error → Retry
```

弹窗和抽屉还要确认：

- 打开和关闭入口；
- 遮罩、Esc 和关闭按钮行为；
- 提交期间是否允许关闭和重复点击；
- 未保存内容是否需要确认；
- 内容超长时实际滚动区域；
- 提交失败后是否保留用户输入；
- 成功后是否刷新列表或详情；
- 刷新、返回和分享链接是否保持正确位置；
- 并发修改是否提示版本冲突。

Make 中的空回调、本地数组和演示统计只能作为视觉或交互参考，不能直接视为真实功能。

如果代码或 Make 存在某个状态而 Design 没有单独设计，必须登记为“Design 未提供独立状态”，不能默认宣称该状态已经对齐。

## 7. 业务与后端边界

```text
Figma 决定显示方式
Make 参考交互方式
真实系统决定是否成功以及何时成功
```

因此：

- 真实接口失败时不能显示假成功；
- 没有持久化接口时不能用前端数组伪造保存；
- 权限、审计、并发、版本和幂等校验不能被视觉实现绕过；
- 设计稿存在但后端尚未支持的入口，应保留真实失败反馈并记录遗留问题；
- 当前系统已有但新版设计没有表达的功能，也不能擅自删除，需记录并等待产品确认。

## 8. 验证要求

### 代码验证

按改动范围执行：

```text
npm run typecheck
npm run build
相关单元测试或接口测试
git diff --check
浏览器控制台和网络请求检查
```

### 页面验证

- 使用与 Design 尽可能一致的 viewport、DPR、浏览器缩放和字体加载状态；
- 使用相同的文案、标点和测试数据比较自适应尺寸；
- 保留 Design 和实际页面的同状态截图；
- 对关键节点保留 computed style 和 bounding box；
- 检查空数据、单条数据、大量数据、长标题、长描述、失败、加载、权限不足、重复点击、窄屏和超长抽屉内容。

不能只根据一张截图或肉眼观感判断整个页面已经完成。

## 9. 对齐结论等级

### 完全对齐

Design、Make、浏览器实际结果和关键状态均已核对。

### 视觉已对齐

主要视觉已完成，但后端、真实接口或部分业务状态尚未完成。

### 部分对齐

只完成了目标区域，页面其他区域或部分状态尚未验收。

### 待确认

Design、Make、现有业务或产品规则存在冲突，需要确认后继续。

只有“完全对齐”可以使用“已完成 Figma 对齐”。其他结论必须明确未完成范围和风险。

## 10. 遗留问题登记

无法在当前任务内解决的问题统一写入 `设计/遗留问题.md`，每条至少包含：

```text
页面 / Figma 节点
当前代码行为
Design 表达
Make 表达
差异类型：视觉 / 交互 / 后端 / 业务
影响范围和风险
当前临时处理
后续动作：补设计 / 补前端 / 补后端 / 产品确认
```

必须双向登记：

1. Design / Make 有，但系统缺少的能力；
2. 系统已有，但 Design / Make 没有表达的功能、字段、状态或入口。

## 12. 快速检查清单

```text
[ ] 已确认准确的 Design 节点和 Make 代码
[ ] 已检查 Git 分支、提交和未提交修改
[ ] 已列出页面全部区域和状态
[ ] 已建立 Design / Make / 当前代码对照表
[ ] 已核对尺寸、字体、颜色、间距、图标和盒模型
[ ] 已核对 Hover、Focus、Selected、Loading、Disabled 和 Error
[ ] 已检查弹窗、抽屉、菜单定位和滚动
[ ] 已检查长文本、大量数据、空态和窄屏
[ ] 已区分视觉、交互、后端和业务差异
[ ] 已完成匹配范围的类型检查、构建或测试
[ ] 已保留截图、computed style 和 bounding box 证据
[ ] 已登记遗留问题和回滚信息
[ ] 已按等级给出对齐结论
```
