# 前端模块职责与大文件治理基线

## 目标

避免新前端形成职责失控、难以理解和难以验证的模块。文件行数和体积只用于发现需要人工审查的候选项，不是强制拆分标准，也不是代码质量结论。

拆分的目标必须是改善职责边界、依赖关系、类型安全、复用价值或可测试性。一个职责单一、依赖清楚、类型完整且容易验证的 900 行文件，可以优于一个被拆成多个纯透传组件和无类型参数包的 700 行文件。

## 扫描命令

```bash
npm run quality:large-files
```

默认采用两级数值标准：

- 大文件审查候选：单文件大于等于 1500 行，或大于等于 100 KB。
- 高风险审查候选：单文件大于等于 3000 行，或大于等于 150 KB。

大文件候选需要进行职责审查；高风险候选应优先审查并记录结论。命中任一级别都不表示“必须拆分”。该命令不得单独作为 CI 失败条件，也不得用于考核拆分后的文件行数。

可在命令前通过环境变量临时调整审查提示值：

```bash
LARGE_FILE_REVIEW_LINES=1800 LARGE_FILE_REVIEW_KB=120 LARGE_FILE_CRITICAL_LINES=3500 LARGE_FILE_CRITICAL_KB=180 npm run quality:large-files
```

## 是否拆分的判断依据

只有出现以下一种或多种实际问题时，才应考虑拆分：

1. 一个模块同时承担多个可以独立描述、独立演进的业务职责。
2. 状态、事件和副作用互相缠绕，修改一个功能容易影响无关功能。
3. 依赖数量或传播层级过多，调用方无法看清组件真实输入输出。
4. 存在可以形成稳定契约的复用逻辑、领域逻辑或视图区域。
5. 关键逻辑无法被独立测试，或回归验证必须依赖整个页面。
6. 文件长期成为多人修改冲突点，并且冲突对应清晰的职责边界。

以下情况不能作为拆分理由：

1. 仅仅命中大文件或高风险文件的数值标准。
2. 仅仅为了让质量扫描数量下降。
3. 通过压缩 import、声明、模板或样式减少行数。
4. 把大量 props、事件或状态塞进 `Record<string, any>`、`any` 或单个 `v-bind` 参数包。
5. 新增只负责转发全部参数、没有形成业务契约的中间组件。
6. 把仍然高度耦合的代码移动到另一个文件，但没有减少依赖和认知复杂度。

## 合理拆分的执行规则

1. 修改前先说明当前职责问题、拟形成的边界以及预期收益。
2. 优先抽取名称清楚、状态输入输出明确且能够独立验证的业务边界。
3. 新边界必须有明确 TypeScript 类型，不得因拆分引入新的 `any` 或隐藏依赖。
4. 组装层应保持依赖可见；大规模参数转发应按领域分组，不能用无类型对象掩盖复杂度。
5. 拆分后应降低耦合、重复或测试成本；如果只降低了父文件行数，应撤销或重新设计该方案。
6. 每次只处理一个职责边界，并运行与影响范围匹配的类型检查、测试、构建或浏览器回归。
7. 视觉重构之外的内部拆分不得改变既有 DOM 语义、样式、交互和业务行为。
8. 中文源码和文案文件禁止整文件重写，优先使用小范围 patch。

## 完成标准

一次拆分只有同时满足以下条件才算有效优化：

- 新模块可以用一句话说明单一职责。
- 输入、输出、事件和副作用具有明确类型和所有权。
- 原模块的依赖数量、分支复杂度、重复逻辑或测试难度至少有一项得到实际改善。
- 没有用纯透传层、巨型参数包或格式压缩掩盖复杂度。
- 类型检查和相关行为验证通过，且前端视觉与交互保持不变。
- 行数下降可以是结果，但不能是验收目标。
